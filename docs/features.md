# Causal feature windows

MCE-3 features consume only canonical `BarObservation` records from `CausalDataStore`. They never call providers or read the wall clock. `TrendFeatureEngine.compute(store, as_of_ns)` receives an explicit time and configuration. The engine rejects an injected calendar whose schedule settings differ from the fingerprinted market configuration. The feature reader accepts only bars from the configured provider source with `effective_timestamp_ns <= as_of_ns`, completed bounds, and a fully regular XNYS interval (`bar_start_ns` through `bar_end_ns - 1`). The price convention is the completed bar **close**; session return alone uses the first completed regular bar's **open** as its reference. Quotes and trades are not mixed into trend features.

`WindowSpec(name, unit, length)` is immutable and serializable. Units are elapsed nanoseconds, observation count, current trading session, and prior exchange trading days. The default horizon names and sizes are `1m`, `5m`, `15m`, `30m`, `1h`, `session`, `1d`, `5d`. Names are part of the output contract. A count window takes the most recent N available regular bars; it does not imply a fixed elapsed duration.

For an elapsed window of length `L` at explicit `T`, the reference is the last completed regular bar with end time at or before `T-L`, no more than `min(cadence,L)` before that boundary. The current price is the latest completed regular close in `[T-L,T]`. Both must be effectively available by `T`. Window bars themselves have end times in `[T-L,T]`; the boundary is inclusive. If the reference is absent, the return is `null`. `expected_count = floor(L/cadence)+1`; observed coverage counts available bars and a distinct reference, capped at 1. Gaps are never synthesized. If a bar's effective time is delayed, the bar remains invisible until that time even when its interval has ended. Regression uses the actual elapsed timestamps of available bars, not a fabricated regular grid.

The `session` reference is the **open** of the first available completed regular bar of the latest observed trading date. It becomes usable only when that bar completes and is effective. The current value is the latest completed regular close. A missing initial bar changes the reference to the first observed bar and reduces interval coverage. Session coverage compares completed bars with the expected count up to the current bar, using the configured cadence and the calendar's actual open. Early closes use their shortened schedule.

For `1d` or `5d`, the reference is the close of the bar ending **exactly at** the regular close of the first or fifth prior XNYS trading session, counted from the latest observed regular bar's trading date. The current value is that latest observed close, including an intraday close; the current day's final close is never read before it exists. A missing prior closing bar yields `null`. Holidays and weekends do not count as trading days. At the configured calendar's leading edge, unavailable prior sessions yield missing data rather than an exception.

Feature names use `trend.<family>.<symbol>.<horizon>` for returns, such as `trend.return.SPY.5m`, and `trend.<diagnostic>.<symbol>` for other scalar snapshot values. The typed result retains richer counts, coverage, flags, regression diagnostics, and contributors; the snapshot projection includes only available finite scalar values. This naming is intended to remain stable for stored historical outputs.

The store remains bounded by `replay.max_observations`. Elapsed/session queries use event-time indexes, and count windows scan backward only until they have enough available regular bars. Repeated snapshots still recalculate diagnostics for each selected window; incremental regression state is a later optimization, not a separate source of truth.

## Realized volatility (MCE-4)

`RealizedVolatilityEngine` consumes the same causal canonical store with an explicit `as_of_ns`, configured source, and XNYS calendar. Intraday windows use completed cadence bars within the actual regular session; daily estimators use full-session OHLC available only after that session completes. Default intraday windows are `5m`, `15m`, `30m`, `1h`, and `session`; default daily windows are `5d`, `10d`, `20d`, and `60d`. A daily return window needs one extra completed session for its first close reference. Gaps reduce coverage rather than creating artificial bars.

Typed per-symbol results expose raw intraday realized/bipower variation and semivariance, separately named annualized daily estimators, short/medium/long context, prior-only percentile and robust z-score, and quality. The weighted market volatility context uses available symbols' medium close-to-close estimates; the volatility score uses available symbols' prior-only short-window percentiles. Both require a minimum symbol fraction. They are observed measurements, not forecasts or categorical regimes. See [volatility engine](volatility-engine.md) for exact formulas, units, quality rules, and stable feature names.

## Market breadth (MCE-5)

`BreadthFeatureEngine` reads a point-in-time constituent snapshot and completed regular-session bars at an explicit `as_of_ns`. Each member's latest causal price is compared with the previous XNYS trading-session close. Missing or stale members remain in the expected count but are excluded from directional and return calculations. Configurable 5/20/60 prior-session close references measure participation above historical levels. The typed result also reports equal and point-in-time weighted returns, index-proxy divergence, high/low participation, breadth momentum, contribution concentration, coverage, and score terms. The headline breadth score is a transparent combination of net advances and reference participation, gated by member coverage. It is neither trend nor a regime label. See [breadth engine](breadth-engine.md) for exact formulas, membership/survivorship rules, and stable names.

## Sector and relative-strength context (MCE-6)

`SectorFeatureEngine` reads a point-in-time sector assignment snapshot, causal completed regular-session bars, and an explicit clock. Sector returns are separate equal-weight, validated point-in-time weighted, and optional proxy series. Relative returns compare equal-weight sectors to a configured broad reference over matching causal horizons. The typed result includes sector breadth, composite daily realized-volatility context, ranked relative-strength scores, persistence, rotation, coverage, and quality. Future reclassification, weight updates, and bars do not change past results. Snapshot projection fills sector scores and scalar evidence without assigning regimes. See [sector engine](sector-engine.md) for formulas and feature names.

## Correlation and systemic co-movement (MCE-7)

`CorrelationFeatureEngine` builds Pearson and optional Spearman matrices from causally available, completed regular-session log returns on a shared timestamp intersection. The medium intraday window is the primary matrix; configurable short/long intraday and optional completed-session daily horizons provide context. The typed result contains coverage and missing/stale diagnostics, raw and point-in-time weighted pairwise correlation, fixed identity shrinkage, eigenvalue share and effective dimension, prior-only historical percentile and changes, optional sector-pair summaries and deterministic groups, and a bounded systemic co-movement score. Snapshot projection fills `correlation_score` and scalar `correlation.*` evidence while leaving categorical regimes unknown. Correlation dispersion describes the spread of pairwise correlations; it is separate from return dispersion. See [correlation engine](correlation-engine.md) for formulas, causality, quality, and stable names.

## Cross-sectional dispersion (MCE-8)

`DispersionFeatureEngine` measures cross-sectional differences in causally available constituent returns over configurable horizons. It reuses point-in-time breadth membership and sector assignments, reports equal-weight population return std plus optional validated weighted std, robust/tail moments, upside/downside and higher moments, sector and volatility spread, exact within/between-sector variance, movement HHI, and prior-only historical percentile/shock/persistence. Optional same-clock sector, realized-volatility, and correlation feature results add context without a circular engine dependency. Snapshot projection fills `dispersion_score` and scalar `dispersion.*` evidence, preserving unknown categorical regimes. See [dispersion engine](dispersion-engine.md) for formulas, units, causality, quality, and stable names.

## Liquidity and market stress (MCE-9)

`LiquidityStressFeatureEngine` measures completed regular-session volume, close-price dollar volume, same-elapsed-time prior-session RVOL, Amihud-style illiquidity, actual fresh quoted spreads, overnight gaps, coverage, and trading concentration for a point-in-time universe. It consumes optional same-clock MCE-4 through MCE-8 context to form a transparent continuous stress score with reconciled contributors; caller-supplied prior stress observations yield percentile, change, acceleration, and persistence. `liquidity_score` is higher for favorable liquidity; `stress_score` is higher for observed strain. Missing/stale inputs remain unavailable, and the snapshot projection preserves unknown categorical regimes. See [liquidity and stress engine](liquidity-stress-engine.md) for exact formulas and stable names.

## Deterministic market regimes (MCE-10)

`MarketRegimeEngine` consumes already computed, same-clock continuous evidence from prior feature engines. Configurable thresholds classify direction, trend, breadth, volatility, liquidity, correlation, dispersion, stress, and sector rotation separately. An ordered, auditable rule table synthesizes one headline regime; typed conflicts and a bounded evidence-strength score show why it was selected. Explicit prior regime history supplies causal hysteresis and transitions, with no hidden mutable state. The optional snapshot projection populates existing schema-1.0 categorical fields and retains detailed `regime.*` evidence in feature values. See [regime engine](regime-engine.md) for the rule table, boundary behavior, quality gates, and replay semantics.

## Regime transitions and stability (MCE-11)

`RegimeTransitionAnalyticsEngine` reads explicit MCE-10 regime history, sorted and indexed by observation time. It counts observed headline and dimension changes, completed dwell episodes, retrospective exit frequencies, duration-weighted occupancy, churn, reversals, synchronized changes, and temporal stability over configurable XNYS trading-session windows. Gaps and inadequate history withhold derived stability instead of creating false certainty. The optional projection adds `regime_transition.*` values without changing the MCE-10 headline. See [regime transition engine](regime-transition-engine.md) for exact formulas, units, quality gates, and the distinction between historical frequency and prediction.

## Statistical preparation (MCE-12)

`mce.statistical` defines an 18-feature ordered schema, constructs causal point-in-time rows from completed context snapshots, retains optional missingness and upstream quality, fits median imputation/scaling only on explicit training rows, and creates XNYS session-based walk-forward splits with embargo. Latent-state profiles, canonical label ordering and descriptive evaluation are separate from MCE-10 deterministic regime fields. No HMM is fitted or projected. See [statistical regime modeling](statistical-regime-modeling.md) for the schema, formulas, leakage boundaries and HMM preparation.
